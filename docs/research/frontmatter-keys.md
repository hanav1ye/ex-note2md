# 仕様: frontmatter の項目別の出力制御とキー名の変更

**作成日**: 2026-10-10
**状態**: 仕様確定・実装前（未決は実装中に決められるもののみ）
**目的**: 読込側（Dataview など）の命名規則に合わせられるようにする

## やること

1. frontmatter の項目ごとに **出力する / しない** を選べる
2. 項目ごとに **キー名を変えられる**（例: `published` → `published_at`）
3. 変更後、既存ファイルを **設定に合わせて揃える**

## 決定事項

### 1. 更新時は管理キーのブロックを作り直す

これまでの「1 行ずつ足す / 書き換える（upsert）」をやめ、**拡張機能が管理するキーをまとめて生成し直す**。

| 区分 | キー | 扱い |
|------|------|------|
| **作り直す** | `title` `source` `note_id` `author` `published` `like_count` `page_view_count` `impression_count` `stats_updated_at` | 設定に従って生成。ON/OFF と改名が効く |
| **据え置き** | `tags` `converted_at` | 既存の値をそのまま引き継ぐ（下記） |
| **触らない** | 利用者が自分で足したキー（`status` など） | そのまま残す |

**なぜ据え置きが要るか**

- `tags` は **popup で利用者が選んだもの**で、note 側のデータではない。API の `hashtag_notes` は別物なので、再生成すると利用者の選択が失われる
- `converted_at` は「変換した日時」。再生成で現在時刻を入れると意味が「最終更新日時」に変わってしまう

**この方式で解決すること**

- 改名時の二重登録が構造的に起きない（旧ブロックごと作り直すため）
- 「出力しない」にした項目が既存ファイルから消える
- 変換時と更新時で整形がずれる問題が消える（コードが 1 本になるため、`tests/conversion-unit.test.mjs` のパリティテストは役目を終える）
- upsert の挿入位置アンカー（`published` / `author` の後ろに挿す）が不要になる

### 2. 値は note の最新に追従する

`title` `author` `published` `source` は、更新のたびに note の最新値へ揃える。

実際に変わるのは数（スキ数・ページビュー・インプレッション）がほとんどで、タイトル等が変わるのは稀。変わったときに揃うほうが「最新にする」という機能の性格に合う。

**vault 側で手直ししていた場合は上書きされる。** これは仕様として README に明記する。

**追加の通信は発生しない。** 再生成に必要な値は、スキ数取得で既に叩いている `/api/v3/notes/{id}` の応答に揃っている。

| frontmatter | API のフィールド |
|-------------|-----------------|
| `title` | `name` |
| `author` | `user.urlname` |
| `published` | `publish_at` |
| `like_count` | `like_count` |
| `note_id` | `key` |
| `source` | `note_url` |

### 3. 順序は「名前」ではなく「項目」に紐づける

```
title → source → note_id → author → published
→ like_count → page_view_count → impression_count → stats_updated_at
→ tags → converted_at
→ （利用者が足した未知のキー）
```

`tags` を `note_tags` に改名しても **tags という項目の位置は動かない**。
未知のキーは相対順序を保ったまま末尾へまとめる。

### 4. `note_id` は固定

ON/OFF も改名も不可。理由は 2 つ。

1. `resolveNoteId` が記事を特定するのに使っている（`note_id` → `source` → ファイル名の順）
2. 書き込み直前の「**このファイルはまだ同じ記事か**」の照合に使っている。これが外れると「対象記事以外を更新しない」という保証が失われる

`note_id` が常に出力されるなら第一候補で必ず解決できるため、**`source` は ON/OFF も改名も自由にしてよい。**

### 5. キー名は英数字のみ

```
^[A-Za-z_][A-Za-z0-9_-]{0,19}$
（1〜20 文字 / 英字か _ で始まる / 英数字と _ - のみ）
```

既定キーの最長は `impression_count` と `stats_updated_at` の 16 文字なので余裕がある。

**日本語を許さない理由**

- 改名の目的が「読込側に合わせる」ことなので、Dataview が素直に扱える英数字が有利（日本語キーは `file.frontmatter["公開日"]` のようなブラケット記法が必要になる）
- **見た目が同じで別物になる**。`グ`(U+30B0) と `グ`(U+30AF U+3099) は画面上は区別できないが別キーとして扱われる。Mac と Windows で入力すると起こりうる。目視で発見できない二重化を持ち込むことになる
- 全角コロン（`公開日：`）が混ざると frontmatter が壊れる。IME を使う以上必ず起こる
- いまの `splitFrontmatter` は「YAML のキー行が 1 つ以上あること」を `[A-Za-z_]` 始まりで判定している。日本語を許すとこの安全装置（水平線に挟まれた本文を frontmatter と誤認しない）が緩む

日本語で表示したい場合は **Obsidian 側のプロパティ表示名**で対応できる（ファイルの中身は英数字のまま）。

**その他の検証**

| 条件 | 扱い |
|------|------|
| 空文字 | 不可 |
| 他の項目と同じ名前 | 不可 |
| `note_id` | 不可（固定キー） |
| `tags` / `aliases` / `cssclasses` など Obsidian が特別扱いする名前 | 警告を出すが禁止はしない |

### 6. 既存ファイルへの反映は「数値を更新」に相乗りする

**専用の権限取得も専用の走査も設けない。** ブロックを作り直す方式にした時点で、
移行は「数値を更新」のついでに無料でついてくる。

```
いまの「数値を更新」:
  フォルダの権限を取る（ダイアログ 0〜1 回）
  → .md を走査
  → frontmatter のブロックを作り直す  ← ここで旧名が新名に置き換わる
```

**新しいダイアログは 1 つも増えない。**

**なぜ全フォルダの一括走査にしないか**

権限はディレクトリハンドル単位なので、5 つのプリセットをまとめて 1 回の許可で通すことは
仕組み上できない。`requestPermission` はユーザー操作の直後でないと通らず、
最初のダイアログで利用者が操作した時点でその状態は消費されるため、
**1 クリックで複数フォルダの許可を取ることはできない前提で設計する。**

共通の親フォルダ（vault ルート）を 1 つ選んでもらえば 1 回で済むが、
プリセットとは別の概念が増え、別ドライブに散っている場合は成立しないため採らない。

**遅延しても二重化しない。** 保留中の旧名を持っているので、いつ更新されても
「旧名の行を新名へ書き換える」になる。旧名が残ったまま新名が増える経路は存在しない。

| タイミング | 起きること |
|-----------|-----------|
| 改名直後 | ファイルは旧名のまま（何も起きない） |
| 次に「数値を更新」したとき | 旧名 → 新名へ揃う。ダイアログは普段どおり |
| ずっと更新しない | 旧名のまま。壊れてはいない |

**おまけとして「いま揃える」を置く。** 待てない人向けに、設定画面からフォルダごとに
`[許可して実行]` を押せるようにする。押した分だけダイアログが 1 回ずつ出る。
プリセットを 1 つしか使っていなければ 1 クリック 1 ダイアログで終わる。
この経路は通信を伴わない（行の書き換えだけなので、note への問い合わせは 0 回、
ログイン不要、間隔待ちも不要。数百件でも数秒）。

既存の安全装置はそのまま使う。

- frontmatter に YAML のキー行があること
- `note_id` が解決できること
- **書き込み直前に読み直して照合**してから書く
- 値が同じファイルは書き込まない

**名前の衝突はスキップして報告する。** 既に `note_tags` を自分で使っているファイルで `tags` → `note_tags` を実行した場合、マージも上書きもせず対象外にし、「衝突 N 件」として出す。

### 7. 旧名は「保留中の 1 件」だけ持つ

永続的な履歴は持たない。移行が完了したら捨てる。

```
改名 → 旧名を保留として記録 → 移行を実行 → 完了したら破棄
```

- 中止した場合は**保留のまま**。あとから「揃える」を押せば続きができる
- 保留中にもう一度改名しても、保持するのは**最初の旧名**（実ファイルに残っている方）
- 既定名（`published` など）は常に照合候補に含める。この機能より前に保存したファイルも 1 回で揃う

**なぜ履歴を持たないか**

「あり得る名前を永久に抱える」形にすると、別端末・別フォルダ・古いバックアップまで考え始めてきりがなく、しかも完全にはならない。保留 1 件なら**自分で片付く一時的な状態**で済む。

**残る隙間**: プリセットフォルダの外に移したファイル、別端末のファイルには届かない。ただしその記事をもう一度変換すればファイルごと置き換わるので自然に解消する。

## 保存するデータ

```json
"frontmatterKeys": {
  "published": { "enabled": true, "name": "published_at", "pendingOldName": "published" },
  "author":    { "enabled": false, "name": "author" }
}
```

**未設定なら現在とまったく同じ出力**になること。1 バイトでも変わると、既存利用者の次回更新で全ファイルが書き換わる。

設定のインポート / エクスポートの対象に含めるかは要検討（vault は共有されるが設定は端末ごとのため、混在すると二重化の原因になる）。

## 変更を伝える

「設定を変えたが、まだ既存ファイルに反映されていない」状態が見えないと不親切なので、
反映されるまで残り続ける表示を置く。

### 設定画面：保留中の変更

status のような一時表示ではなく、**反映が済むまで残る枠**にする。ページを開き直しても出る。

```
┌─────────────────────────────────────────────────┐
│ ⏳ 既存ファイルへの反映待ち                        │
│                                                 │
│   published  →  published_at                    │
│   author     →  出力しない                       │
│                                                 │
│ 次回「数値を更新」を実行したときに反映されます。      │
│                                                 │
│                              [ いま揃える ]      │
└─────────────────────────────────────────────────┘
```

- **何が変わるのかを 1 行ずつ**出す（「設定を変えました」だけでは何が起きるか分からない）
- **いつ反映されるか**を明記する
- 反映が終わったら**自動で消える**

**保存先フォルダが未設定でも表示する。** 反映先がなくても「いつか設定したときに反映される」
ことを伝える意味があるため（2026-10-10 決定）。

### 「数値を更新」側にも出す

実行する場所にも書かないと、設定画面を見ていない利用者には伝わらない。

確認ダイアログに 1 行足す。

```
「Obsidian Inbox」配下で .md を 842件 見つけました。
うち 842件 を更新対象として note へ問い合わせます。

frontmatter のキー名の変更も反映します（published → published_at）。

ファイルを書き換えます。取り消しはできません。
```

完了メッセージにも件数を足す。

```
完了: 更新 842件 / 変更なし 0件 / 対象外 0件 / 失敗 0件
 / うちページビュー数まで更新 120件 / キー名を揃えた 842件
```

### 文言

| キー | 日本語 | English |
|------|--------|---------|
| `options.frontmatter.pendingTitle` | 既存ファイルへの反映待ち | Waiting to be applied to existing files |
| `options.frontmatter.pendingHint` | 次回「数値を更新」を実行したときに反映されます。 | This will be applied the next time you run “Refresh stats”. |
| `options.frontmatter.pendingRename` | {from} → {to} | {from} → {to} |
| `options.frontmatter.pendingDisable` | {from} → 出力しない | {from} → not written |
| `options.frontmatter.applyNow` | いま揃える | Apply now |
| `options.likeCount.confirmKeyRename` | frontmatter のキー名の変更も反映します（{changes}）。 | Frontmatter key changes will also be applied ({changes}). |
| `options.likeCount.doneKeyRename` | / キー名を揃えた {count}件 | / {count} with key names aligned |
